Section 1 Core Keywords & Concepts

Master these 8 foundational keywords before diving into the code for Section 1 (Docker Infrastructure & Centralized Config):

NETWORKING
Docker Bridge Network (dropzone-net)
An isolated virtual software network created by Docker Compose that allows all 14 containers to communicate with each other using container hostnames (e.g. postgres:5432, kafka:29092) rather than host IP addresses.
dropzone-net DNS Resolution Network Isolation
DATA PATTERN
Database-per-Service Isolation
Each microservice connects exclusively to its own dedicated PostgreSQL database (e.g. dropzone_user, dropzone_order). Services are strictly forbidden from executing cross-database joins or accessing another service's tables directly.
Loose Coupling 6 Isolated DBs ACID Boundary
CDC PREREQUISITE
Logical WAL (wal_level=logical)
PostgreSQL Write-Ahead Logging mode configured to decode row-level insert/update/delete change events into a structured stream. This allows Debezium CDC to read database mutations in real time without querying the database tables.
wal_level=logical Debezium Ingestion Zero SQL Overhead
CONFIG PATTERN
Spring Cloud Config Server
A centralized HTTP server running on port 8888 that acts as the single source of truth for all YAML configurations, environment variables, database credentials, and Kafka topic names across the entire microservices fleet.
@EnableConfigServer Port 8888 Native Profile
BOOTSTRAP
Spring config.import
The modern Spring Boot 3 mechanism replacing bootstrap.yml. On startup, the microservice halts bean creation, reaches out to http://localhost:8888, loads its specific environment YAML, merges it with global properties, and then initializes.
spring.config.import Spring Boot 3 Zero Hardcoding
RESILIENCE
Fail-Fast (fail-fast: true)
A safety setting that immediately crashes the microservice JVM with a clear error message during startup if Config Server is unreachable, preventing services from booting with missing database credentials or default fallback configurations.
fail-fast: true Crash Early Zero Half-Started Apps
DRY CONFIG
Global Inheritance (application.yml)
A central YAML file inside config-repo/ containing cluster-wide shared properties (Eureka URL, Kafka serializers, OpenTelemetry tracing config) that are automatically inherited by every microservice without duplication.
config-repo/application.yml Inheritance Hierarchy DRY Principle
MIGRATIONS
Flyway Schema History Isolation
Automated database version control executing SQL scripts on startup. Setting service-specific history tables (e.g. flyway_schema_history_audit) prevents lock collisions and metadata corruption when multiple services share database clusters.
flyway.enabled: true V1__init.sql Zero Manual SQL
Section 1 Deep-Dive

Docker Infrastructure & Centralized Config Backbone

Welcome to Section 1. This is where the entire DropZone platform starts. Before writing or running any Java microservice, you must understand two things: how the backing infrastructure containers are configured and how microservices retrieve their YAML configuration dynamically on boot.

1.1 The 14-Container Infrastructure Stack (`docker-compose.yml`)

DropZone provisions 14 isolated backing infrastructure containers joined by a dedicated bridge network called dropzone-net. Below is the complete, line-by-line commented configuration for every service container.

1.1.1 PostgreSQL 16 Relational Engine (Port 5432)

Role: Hosts 6 isolated relational databases: dropzone_user, dropzone_event, dropzone_inventory, dropzone_order, dropzone_payment, and dropzone_audit.

docker-compose.yml > postgres (PostgreSQL 16 with Logical WAL) YAML 
  postgres:
    image: postgres:16-alpine                                    # Lightweight alpine base image for PostgreSQL 16
    container_name: dropzone-postgres                            # Fixed container name for internal DNS resolution
    # wal_level=logical: Instructs PostgreSQL to emit structured row data into WAL for CDC
    # max_wal_senders=10: Maximum number of concurrent streaming replication processes (Debezium + replicas)
    # max_replication_slots=10: Prevents Postgres from deleting WAL logs before Debezium has consumed them
    command: postgres -c wal_level=logical -c max_wal_senders=10 -c max_replication_slots=10
    ports:
      - "5432:5432"                                              # Host:Container port mapping for external psql access
    environment:
      POSTGRES_USER: dropzone                                    # Master superuser name
      POSTGRES_PASSWORD: dropzone_secret_password                 # Master database password
      POSTGRES_DB: dropzone                                      # Default initial database created on first startup
    volumes:
      - postgres_data:/var/lib/postgresql/data                   # Named volume to persist table data across restarts
      - ./docker/postgres/init-databases.sql:/docker-entrypoint-initdb.d/init-databases.sql:ro # Init script creating all 6 microservice DBs
    networks:
      - dropzone-net                                             # Attach to the unified bridge network
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U dropzone"]              # Checks if postgres engine is accepting socket connections
      interval: 5s                                               # Frequency between health probes
      timeout: 5s                                                # Maximum probe response wait time
      retries: 5                                                 # Mark unhealthy after 5 failed attempts

1.1.3 Zookeeper & Apache Kafka Event Streaming (Port 9092)

Role: High-throughput, distributed event log for microservice domain events (order-events, payment-events) and Debezium CDC ingestion.

docker-compose.yml > zookeeper & kafka YAML 
  zookeeper:
    image: confluentinc/cp-zookeeper:7.5.0                       # Confluent enterprise-grade Zookeeper image
    container_name: dropzone-zookeeper                          # Container name for cluster coordinator
    environment:
      ZOOKEEPER_CLIENT_PORT: 2181                                # Internal port where Kafka connects to Zookeeper
      ZOOKEEPER_TICK_TIME: 2000                                  # Basic time unit in milliseconds for session heartbeats
    networks:
      - dropzone-net                                             # Shared internal bridge network

  kafka:
    image: confluentinc/cp-kafka:7.5.0                           # Confluent Kafka 7.5 broker image
    container_name: dropzone-kafka                              # Internal network DNS alias for microservices
    ports:
      - "9092:9092"                                              # Host port for developer workstations and UI tools
    depends_on:
      - zookeeper                                                # Ensures Zookeeper is running before broker boots
    environment:
      KAFKA_BROKER_ID: 1                                         # Unique broker numeric identifier in cluster
      KAFKA_ZOOKEEPER_CONNECT: zookeeper:2181                    # Host and port to connect to Zookeeper coordinator
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: PLAINTEXT:PLAINTEXT,PLAINTEXT_HOST:PLAINTEXT # Protocol mappings for internal/external
      # Dual-listener setup:
      # PLAINTEXT://kafka:29092   -> Used by other Docker containers inside 'dropzone-net'
      # PLAINTEXT_HOST://localhost:9092 -> Used by host applications & local Java debuggers
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:29092,PLAINTEXT_HOST://localhost:9092
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1                  # Single broker dev environment needs replication factor = 1
      KAFKA_AUTO_CREATE_TOPICS_ENABLE: "true"                    # Automatically provision topics upon first message publish
    networks:
      - dropzone-net                                             # Shared Docker network
    healthcheck:
      test: ["CMD-SHELL", "nc -z localhost 9092 || exit 1"]     # TCP socket port ping verification
      interval: 10s                                              # Check every 10s
      timeout: 5s                                                # 5s probe timeout
      retries: 5                                                 # 5 attempts

1.1.4 Debezium 2.5 Change Data Capture (Port 8083)

Role: Tails PostgreSQL Write-Ahead Logs (WAL) and automatically streams row modifications into Kafka without modifying application business code.

      OFFSET_STORAGE_REPLICATION_FACTOR: 1                       # Replication factor for single-broker setup
      STATUS_STORAGE_REPLICATION_FACTOR: 1                       # Replication factor for single-broker setup
    networks:
      - dropzone-net                                             # Shared Docker network

1.2 Centralized Config Architecture & Dynamic Bootstrap

In enterprise microservice platforms, credentials, database connection strings, and Kafka topic names are never hardcoded inside individual service jars. Instead, DropZone uses Spring Cloud Config Server with a 4-step dynamic bootstrap architecture:

Step 1: The Microservice Local Bootstrap File (`user-service/src/main/resources/application.yml`)

Every microservice has a minimal local application.yml containing zero passwords or database URLs. Its only job is to declare its name and connect to Config Server on startup:

services/user-service/src/main/resources/application.yml YAML 
server:
  port: 8081                                                     # Local HTTP port for this microservice

spring:
  application:
    name: user-service                                           # Unique service identifier passed to Config Server
  profiles:
    active: development                                          # Active profile requesting 'user-service-development.yml'
  config:
    # Tell Spring Boot 3 to fetch remote properties from Config Server at :8888 before initializing beans
    import: "optional:configserver:${CONFIG_SERVER_URL:http://localhost:8888}"
  cloud:
    config:
      fail-fast: true                                            # Halt startup with fatal error if Config Server is offline

eureka:
  instance:
    prefer-ip-address: true                                      # Register IP rather than transient container hostname
    instance-id: ${spring.application.name}:${random.value}      # Unique instance ID for Eureka load balancing
  client:
    service-url:
      defaultZone: ${EUREKA_SERVER_URL:http://localhost:8761/eureka/} # Location of Eureka Service Discovery registry

Step 2: Config Server Engine (`ConfigServerApplication.java` & `application.yml`)

Config Server runs on port 8888 with @EnableConfigServer and uses the native profile to serve YAML files directly from the local config-repo/ directory:

services/config-server/.../ConfigServerApplication.java JAVA 
package com.dropzone.configserver;

import org.springframework.boot.SpringApplication;                // Spring Boot application bootstrapper
import org.springframework.boot.autoconfigure.SpringBootApplication; // Enables auto-configuration and component scanning
import org.springframework.cloud.client.discovery.EnableDiscoveryClient; // Registers Config Server itself in Eureka
import org.springframework.cloud.config.server.EnableConfigServer; // Activates Spring Cloud Config Server REST controllers

@SpringBootApplication                                           // Marks primary Spring Boot entry point
@EnableConfigServer                                              // Exposes /${application}/${profile} configuration REST endpoints
@EnableDiscoveryClient                                           // Enables Eureka client heartbeats so peers can discover config
public class ConfigServerApplication {

    public static void main(String[] args) {
        SpringApplication.run(ConfigServerApplication.class, args); // Starts embedded Tomcat server on port 8888
    }
}
services/config-server/src/main/resources/application.yml YAML 
server:
  port: 8888                                                     # Dedicated port for Centralized Configuration Server

spring:
  application:
    name: CONFIG-SERVER                                          # Registry name visible in Eureka dashboard
  cloud:
    config:
      server:
        native:
          # Search locations: looks inside classpath and relative paths for config-repo directory
          search-locations: ${CONFIG_REPO_PATH:classpath:/config-repo,file:${user.dir}/../../config-repo,file:${user.dir}/config-repo}
  profiles:
    active: native                                               # Activates local filesystem search rather than remote Git

eureka:
  instance:
    prefer-ip-address: true                                      # Broadcast IP address to cluster
    instance-id: ${spring.application.name}:${random.value}      # Unique instance identifier
  client:
    service-url:
      defaultZone: ${EUREKA_SERVER_URL:http://localhost:8761/eureka/} # Register with Eureka cluster

Step 3: Global Shared Configuration (`config-repo/application.yml`)

Any property defined in config-repo/application.yml is automatically inherited by all 11 microservices across the entire cluster:

config-repo/application.yml (Shared Global Microservice Settings) YAML 
# Global base configuration inherited by all 11 microservices
spring:
  eureka:
    client:
      service-url:
        defaultZone: ${EUREKA_SERVER_URL:http://localhost:8761/eureka/} # Uniform Eureka registry location
  kafka:
    listener:
      observation-enabled: true                                  # Enables Micrometer / OTEL tracing across Kafka consumers
    template:
      observation-enabled: true                                  # Enables Micrometer / OTEL tracing across Kafka producers

management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,metrics,traces,env       # Expose essential Actuator observability endpoints
  endpoint:
    health:
      show-details: always                                       # Display full DB, Redis, and disk component health checks
    prometheus:
      enabled: true                                              # Enable /actuator/prometheus metrics scrapers
  metrics:
    export:
      prometheus:
        enabled: true                                            # Export metrics in Prometheus format
    distribution:
      percentiles-histogram:
        http.server.requests: true                               # Track latency percentiles (p50, p95, p99) on HTTP endpoints
  tracing:
    sampling:
      probability: 1.0                                           # 1.0 = Sample 100% of all requests for distributed tracing
  otlp:
    tracing:
      endpoint: ${OTEL_EXPORTER_OTLP_ENDPOINT:http://localhost:4318/v1/traces} # Send trace spans to OTEL Collector

Step 4: Service-Specific Configuration (`config-repo/user-service-dev.yml`)

Each service has its own dedicated YAML file for database credentials, Flyway migrations, and service-specific parameters:

config-repo/user-service-dev.yml (User Service Database & Flyway Config) YAML 
spring:
  datasource:
    # Dynamic PostgreSQL connection URL targeting the dedicated 'dropzone_user' database
    url: ${SPRING_DATASOURCE_URL:jdbc:postgresql://${POSTGRES_HOST:localhost}:${POSTGRES_PORT:5432}/dropzone_user}
    username: dropzone                                           # Database login user
    password: dropzone_secret_password                           # Database password
    driver-class-name: org.postgresql.Driver                     # PostgreSQL JDBC driver class
  jpa:
    hibernate:
      ddl-auto: validate                                         # Do not alter DB schema automatically; validate against Flyway
    show-sql: true                                               # Print formatted SQL statements to stdout for debugging
    properties:
      hibernate:
        dialect: org.hibernate.dialect.PostgreSQLDialect         # Target PostgreSQL dialect
  flyway:
    enabled: true                                                # Run schema migrations on microservice startup
    locations: classpath:db/migration                            # Directory containing V1__init_user_schema.sql scripts
    baseline-on-migrate: true                                    # Baseline existing schema if already present

📊 The 3 Pillars of Observability (Metrics, Logs, Traces)

Full Stack Telemetry
💡 The Hospital Monitoring Analogy

• 1. Metrics (Prometheus): The Heart Rate Monitor — tells you "Heart rate is spiking to 180 BPM!" (e.g. API Error rate > 5%).
• 2. Traces (Tempo + OpenTelemetry): The X-Ray / CT Scan — tracks the exact path a request traveled through 6 microservices: Gateway (10ms) ➔ Order (40ms) ➔ Payment (500ms!).
• 3. Logs (Loki): The Doctor's Notes — the exact error message: NullPointerException at line 42.
• 4. Dashboard (Grafana): The Single TV Screen displaying all three in one unified window!

1. How the 5 Tools Connect
[1. OpenTelemetry Collector (Port 4318)] ──► The Receptionist. Ingests raw telemetry from all Spring Boot apps via OTLP protocol.
      │
      ├──► Sends Traces ────► [Tempo (Port 3200)] (Stores trace spans & call graphs)
      └──► Sends Metrics ───► [Prometheus (Port 9090)] (Stores numbers/counters)

[2. Loki (Port 3100)] ───────────────► Stores indexed logs sent from microservices.

[3. Grafana (Port 3000)] ────────────► The Single Pane of Glass. Correlates Trace ID ➔ Log ➔ Metric!
2. The "Superpower": Trace-to-Log Correlation

In traditional architectures, when an order fails, you grep through 10 separate log files looking for what happened.

In DropZone's stack, every HTTP request receives a unique Trace ID (e.g. c8b3a109f28d). Spring Boot 3 automatically injects this Trace ID into every log line and database query. Inside Grafana, you can click on a slow trace span in Tempo and instantly see the exact error logs in Loki with one click!

⚖️ Feature Breakdown: ZooKeeper vs. Kafka

Architecture Deep-Dive
🤝 How Their Features Connect (The Airport Analogy)
🐘 ZooKeeper (The Airport Tower)
  • Heartbeats: Tracks which planes are in the air.
  • Leader Election: Assigns which plane lands on Runway 1.
  • Catalog (Metadata): Stores the flight schedule board.
  • Failover: If a runway closes, diverts traffic instantly.
⚡ Kafka (The Cargo Planes)
  • High-Volume Cargo: Carries millions of packages (events).
  • Partition Tracks: Has multiple parallel cargo bays.
  • Zero-Copy Speed: Loads/unloads at physical hardware speed.
  • Replay History: Keeps packages in storage for days.

🐘 Why Does Apache Kafka Need ZooKeeper?

Cluster Coordinator
💡 The Traffic Control Tower Analogy

Think of Kafka brokers like airplanes moving cargo (messages), and ZooKeeper as the air traffic control tower.

• Kafka brokers store and stream messages.
• ZooKeeper coordinates the cluster: it tracks which brokers are alive, elects the leader broker, and coordinates topic partition ownership.

1. The 4 Key Jobs of ZooKeeper
1. Controller Election: When multiple Kafka brokers run, ZooKeeper elects one broker as the Controller to manage partition assignments.

2. Broker Heartbeat Membership: Brokers send periodic heartbeats (every 2000ms). If a broker crashes, ZooKeeper detects it and tells other brokers to take over its partitions.

3. Topic Metadata & Partitions: Keeps the catalog of all topics (e.g. order-events), how many partitions they have (P0, P1, P2), and which broker is the active leader for each partition.

4. Access Control Lists (ACLs): Stores cluster security permissions and client quotas.
💡 Does ZooKeeper prevent Kafka from dying?

No, ZooKeeper cannot stop a server from crashing (if a machine loses power or runs out of RAM, it will still die).

What ZooKeeper DOES do:
• Instant Detection (<2s): When a broker dies, its ZooKeeper heartbeat stops and its ephemeral node disappears.
• Automatic Failover: ZooKeeper immediately elects a backup broker to take over the dead broker's topic partitions.
• Zero Downtime for the Cluster: From the outside (your microservices), the overall Kafka system keeps working without human intervention.

❓ Can we run Kafka with NEITHER ZooKeeper NOR KRaft?

Short Answer: No, Kafka cannot start without either ZooKeeper or KRaft.

• Why: Kafka is fundamentally a consensus-driven distributed system. Even on a single machine, it must know how to allocate topic partitions, track consumer group offsets, and manage write locks. That metadata must live in either ZooKeeper or KRaft.

• If you want NO ZooKeeper AND NO KRaft: You would replace Kafka with a simpler single-process message broker like RabbitMQ or Redis Streams (both of which are already running in DropZone!).

2. What is KRaft? (The Future of Kafka without ZooKeeper)

In modern Kafka (v3.0+ and v4.0), Apache introduced KRaft (Kafka Raft Metadata Mode), which removes ZooKeeper entirely by embedding a Raft consensus engine directly inside Kafka itself.

In DropZone's current Docker stack, Confluent Kafka 7.5.0 with ZooKeeper is used for enterprise backward compatibility and seamless integration with Debezium Connect.

3. How Kafka Connects to ZooKeeper
docker-compose.yml (ZooKeeper & Kafka Link) YAML 
  zookeeper:
    image: confluentinc/cp-zookeeper:7.5.0
    environment:
      ZOOKEEPER_CLIENT_PORT: 2181                                # Port Kafka talks to
      ZOOKEEPER_TICK_TIME: 2000                                  # Heartbeat interval (2000ms)

  kafka:
    image: confluentinc/cp-kafka:7.5.0
    depends_on:
      - zookeeper                                                # Boot order guarantee
    environment:
      KAFKA_ZOOKEEPER_CONNECT: zookeeper:2181                    # Connects broker to coordinator

⏱️ Timeline: When Exactly Does Data Get Written to PostgreSQL?

Engine Internals
🎯 Bottom Line: Why This Architecture Exists

Yes, exactly! It gives you two massive wins:
• 🚀 Speed (Latency drops from ~3,000ms down to <10ms): Services get instant event notifications directly off the sequential disk log without waiting for SQL polling intervals.
• 📉 Less Resources (DB CPU usage drops from ~70% to <2%): Zero repeated SELECT queries hammering indexes and disk tables.

⚡ Two Writes Under the Hood

1. Instant sequential WAL append on disk (Microseconds): Client gets `SUCCESS` immediately; Debezium streams it out to Kafka in parallel.
2. Background Table File Flush (Seconds later): Heavy random-access disk updates happen quietly in the background via DB checkpoints.

1. The Complete 5-Step Internal Timeline
Step 1: In-Memory Mutation (Shared Buffers)
  • Microservice executes: UPDATE orders SET status = 'PAID' WHERE id = 101;
  • Postgres modifies the page in RAM buffer (marked as "dirty page").
  • Duration: ~0.05ms

Step 2: WAL Disk Flush (Write-Ahead Log)
  • Before telling the client "success", Postgres appends the exact change into the WAL log and runs fsync() to disk.
  • Debezium reads the event right HERE! (instantly as WAL is written).
  • Duration: ~0.5ms

Step 3: COMMIT Returned to Microservice
  • Postgres responds: UPDATE 1 (Success).
  • The transaction is 100% durable & crash-safe. If power drops now, Postgres will replay the WAL on reboot.

Step 4: Background Table File Flush (Checkpointing)
  • In the background (every few seconds or at checkpoint), PostgreSQL background writer writes dirty RAM pages to the permanent table storage files on disk (e.g. base/16384/...).
  • Duration: Async background (zero client wait)
2. Why Databases Use This Two-Step Write

• Writing directly to table files is slow: Table rows are scattered randomly across huge gigabyte files on disk (Random I/O). Updating them synchronously for every request would destroy performance.
• Appending to WAL is ultra-fast: The WAL is a single sequential file (Sequential I/O). Hard drives and SSDs write sequential logs at maximum hardware speeds (under 1 millisecond).

⚡ Complete Breakdown: PostgreSQL Logical WAL & Debezium CDC

CDC Fundamentals
🌉 Debezium's Exact Role: The Reliable Bridge to Kafka

• Postgres WAL is already there: PostgreSQL writes the WAL file automatically as part of its core storage engine.
• Postgres cannot speak Kafka: Postgres is a database; it has no built-in network connection to Apache Kafka brokers.
• Debezium is the Bridge: Debezium connects to PostgreSQL's replication stream, converts the internal WAL binary events into standardized JSON/Avro messages, and delivers them directly into Kafka topics (with retry cursors, offset tracking, and schema preservation).

💡 The Simple Kitchen Order Analogy

Imagine a restaurant kitchen. When a customer orders pasta, the waiter writes it on a continuous paper notepad (The WAL Log) before the chef cooks it on the pan (The Database Disk).

• Old Polling Method: An auditor runs into the kitchen every 2 seconds, shouting "Did anyone order pasta yet?!" — distracting the chef and wasting energy.
• CDC (Change Data Capture) Method: A helper simply reads the notepad stream as the waiter writes it down and whispers the new orders to the delivery drivers in real time. Zero chef interruption!

1. Step-by-Step Architecture Flow
[1. User Buys Ticket] ──► Order Service writes SQL: INSERT INTO orders (id, user_id, status) VALUES (101, 5, 'PAID');
      │
      ▼
[2. Postgres WAL Write] ──► PostgreSQL writes change to append-only WAL file on disk (takes ~0.5ms)
      │
      ▼
[3. wal_level=logical] ──► Postgres decodes raw disk bytes into JSON data: "Table: orders | New Row: id=101, status=PAID"
      │
      ▼
[4. Debezium CDC Engine] ──► Debezium captures the decoded stream instantly over a replication slot (<10ms latency)
      │
      ▼
[5. Apache Kafka Event] ──► Published to topic dropzone.public.orders for Notification, Audit & Search microservices.
2. Why wal_level=logical is Required

By default, PostgreSQL uses wal_level=replica or minimal. In default mode, the WAL only stores low-level hardware disk bytes (e.g. "Modify offset 0x4F on block 82"). Debezium cannot read table names or column values from raw disk bytes.

Setting wal_level=logical tells PostgreSQL: "Decode and preserve the column names, row IDs, and data values in the stream so external tools can understand what changed."

3. Exact Configuration in DropZone (`docker-compose.yml`)
docker-compose.yml (PostgreSQL Service Settings) YAML 
  postgres:
    image: postgres:16-alpine
    container_name: dropzone-postgres
    # wal_level=logical: Enables logical row decoding for Debezium CDC
    # max_wal_senders=10: Allows up to 10 streaming replication connections
    # max_replication_slots=10: Holds position cursor so logs aren't deleted before Debezium reads them
    command: postgres -c wal_level=logical -c max_wal_senders=10 -c max_replication_slots=10
    environment:
      POSTGRES_USER: dropzone
      POSTGRES_PASSWORD: dropzone_secret_password
    ports:
      - "5432:5432"
