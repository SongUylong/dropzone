How to Use This Guide

Do not read the repository randomly. Follow the chapters in order and keep the code open beside this document. The guide is written for an AI-built codebase where the system appears to work, but you want to understand and personally own every important decision.

The rule for every file you read

Question What you must write down
1. Why does this file exist? The responsibility in one sentence.
2. Who calls or loads it? Framework, controller, service, listener, config loader, CI runner, etc.
3. What does it depend on? Classes, database, Redis, Kafka, RabbitMQ, HTTP service, configuration.
4. What state does it change? Database rows, cache entries, messages, files, nothing.
5. What happens if it fails? HTTP error, retry, rollback, event retry, DLQ, partial failure.
6. How is it tested? Unit test, integration test, contract test, manual test, load test.
7. What breaks if I delete it? This proves you understand its actual role.

EXHAUSTIVE DROPZONE ARCHITECTURE FRAMEWORK & CORE COMPONENT MATRIX:

▶ COMPONENT 1: API GATEWAY & INGRESS ROUTING (Port 8080)

→
• What it is about: The single entry-point for all client HTTP requests entering the DropZone microservices cluster.
→
• Why we use it: Decouples client applications from internal microservice IPs/ports, centralizes authentication checks, and enforces routing policy.
→
• Why we need it: Prevents exposing internal microservices directly to the internet, eliminates CORS duplication across 8 services, and provides central rate-limiting.
→
• How it works: NGINX on edge-01 (192.168.56.10:80) proxies traffic to API Gateway (port 8080). Gateway matches route paths (/api/orders/** -> lb://ORDER-SERVICE), validates Keycloak JWT tokens reactively, strips sensitive headers, and forwards requests.
→
• Verification Checklist:
✓
Verify API Gateway routes resolve via Eureka (lb://SERVICE-NAME).
✓
Test public endpoint access (/api/events) without JWT token.
✓
Test protected endpoint access (/api/orders) with and without valid Keycloak Bearer token.
✓
Inspect gateway logs for MDC traceId propagation and X-User-Id header forwarding.

▶ COMPONENT 2: EUREKA SERVICE DISCOVERY (Port 8761)

→
• What it is about: Dynamic service registry keeping track of every active microservice container instance and its host/port.
→
• Why we use it: Eliminates hardcoded IP addresses and ports between microservices in cloud/container environments.
→
• Why we need it: Supports dynamic horizontal auto-scaling (e.g. order-service-1 and order-service-scaled) and automatic self-healing when instances die.
→
• How it works: Microservices include eureka-client, registering with Eureka Server on infra-01:8761 on startup. They send heartbeats every 30 seconds. Spring Cloud LoadBalancer fetches the registry and balances calls across healthy instances.
→
• Verification Checklist:
✓
Open http://infra-01:8761 to verify all 8 business microservices are registered as UP.
✓
Stop one order-service instance and confirm Eureka deregisters it after lease expiration.
✓
Verify client-side load balancing routes requests to surviving instances without error.

▶ COMPONENT 3: KEYCLOAK IDENTITY & ACCESS MANAGEMENT (Port 8089)

→
• What it is about: OpenID Connect (OIDC) & OAuth2 identity provider handling authentication, user accounts, and role-based permissions.
→
• Why we use it: Offloads user credential storage, password hashing, and token issuance from custom application code to a battle-tested security platform.
→
• Why we need it: Centralizes user security across all microservices, ensuring standardized JWT tokens containing roles (USER, ORGANIZER, SUPPORT, ADMIN).
→
• How it works: Keycloak runs on infra-01:8089. Users authenticate against /realms/dropzone/protocol/openid-connect/token receiving signed RSA JWT access tokens. API Gateway verifies tokens using Keycloak's public JWK set.
→
• Verification Checklist:
✓
Execute setup-keycloak.py to provision the dropzone realm and roles.
✓
Obtain access token via Password grant or Authorization Code flow.
✓
Decode JWT on jwt.io to confirm realm_access.roles and sub claim structure.
✓
Verify 401 Unauthorized returned when passing expired or forged tokens.

▶ COMPONENT 4: APACHE KAFKA DOMAIN EVENT BACKBONE (Port 9092)

→
• What it is about: Distributed append-only event log used for asynchronous inter-service communication.
→
• Why we use it: Decouples business events (PaymentCompleted, OrderConfirmed) from downstream processing systems.
→
• Why we need it: Guarantees high-throughput event streaming, event replay capabilities, and eventual consistency without tight HTTP coupling.
→
• How it works: Kafka Broker runs on infra-01:9092. Payment/Order services produce domain events to topics (order-events, payment-events). Consumer groups (notification-service-group, audit-service-group, inventory-service-group) consume partitions independently.
→
• Verification Checklist:

✓

✓

▶ COMPONENT 5: TRANSACTIONAL OUTBOX & DEBEZIUM CDC

→
• What it is about: Pattern ensuring atomic database updates and event publishing without dual-write inconsistencies.
→
• Why we use it: Prevents data drift where a database commit succeeds but a Kafka network failure drops the event.
→
• Why we need it: Guarantees at-least-once event publication for critical financial and order workflows.
→
• How it works: OrderServiceImpl inserts an OutboxEvent row inside the same PostgreSQL @Transactional commit as the Order entity. Debezium reads PostgreSQL WAL logs and streams outbox rows to Kafka order-events topic automatically.
→
• Verification Checklist:
✓
Verify outbox_event table schema in V3__add_outbox_events.sql.
✓
Inspect OrderServiceImpl.java to confirm Order and OutboxEvent are saved in one transaction.
✓
Verify Debezium container streams committed outbox rows to Kafka in real time.

▶ COMPONENT 6: RABBITMQ WORKER QUEUES (Port 5672)

→
• What it is about: Task-oriented message broker designed for competing background worker jobs.
→
• Why we use it: Handles heavy background operations (PDF rendering, QR code generation, email sending) asynchronously.
→
• Why we need it: Prevents slow PDF compilation or third-party SMTP timeouts from blocking HTTP API request threads.
→
• How it works: Notification Service pushes job payloads (ticket-generation.queue) to RabbitMQ on infra-01:5672. Dedicated workers (TicketWorker, EmailWorker) process jobs with manual ACK and Dead Letter Exchange (DLX) error handling.
→
• Verification Checklist:
✓

✓
Verify ticket-generation.queue, email.queue, and sms.queue definitions.
✓

▶ COMPONENT 7: RESILIENCE4J FAULT TOLERANCE

→
• What it is about: Fault-tolerance library providing Circuit Breakers, Rate Limiters, Time Limiters, and Bulkheads.
→
• Why we use it: Protects synchronous HTTP calls between microservices against cascading failures and thread pool exhaustion.
→
• Why we need it: Prevents a failure in payment-service from hanging HTTP worker threads in order-service.
→
• How it works: PaymentClient.java is annotated with @CircuitBreaker(name="paymentService", fallbackMethod="paymentFallback"). When payment-service fails or times out, the circuit opens, instantly executing fallback methods (returning HTTP 500/503 in 0.01s).
→
• Verification Checklist:
✓

✓
Send order checkout request to order-service.
✓
Confirm order-service remains healthy (UP) and returns fast fallback response in < 10ms.
✓
Verify Circuit Breaker transitions from CLOSED -> OPEN -> HALF_OPEN.

▶ COMPONENT 8: REDIS DISTRIBUTED STATE & FLASH SALE CONCURRENCY (Port 6379)

→
• What it is about: In-memory data structure store used for distributed locks, stock decrements, and waiting room queues.
→
• Why we use it: Ultra-fast sub-millisecond read/write speed under high concurrent traffic bursts.
→
• Why we need it: Protects PostgreSQL from lock contention during high-demand flash sales and prevents ticket overselling.
→
• How it works: InventoryServiceImpl uses Redis atomic decrements (opsForValue().decrement) for ticket stock checks and Sorted Sets (ZSets) for fair waiting room admission.
→
• Verification Checklist:
✓
